# Handoff

This document exists so any AI agent (or human) picking up this project can understand the context, the vision, and how we work together — without re-deriving it from scratch by reading the whole chat history. Read this first. Then read `CHANGES.md` for the detailed, chronological log of what's actually been built and why (including bugs found and how they were diagnosed).

## What this is

A **private fork of Ultrasonic** (the open-source Android Subsonic/Navidrome/Airsonic client), cloned for the user's personal use. Not intended to be pushed to the public GitLab/GitHub upstream or shared. `origin` still points at `gitlab.com/ultrasonic/ultrasonic` — never push there.

## The vision

Turn Ultrasonic from a generic, feature-complete Subsonic client into a **music-only app built for intentional listening**, visually inspired by Spotify. Concretely, that means:

- **Music only.** Podcasts, Video, and Chat have been hidden from the UI (drawer + Home quick-access) because they don't belong in a "pure music player." Their code was deliberately *not* deleted — video support in particular is threaded through shared classes (`Track`, downloads) that music also depends on, so ripping it out is a much bigger, riskier job than hiding a menu entry. If asked to go further, that's a distinct, larger task — don't assume it's wanted.
- **Local player, not a social music network.** The user's own words: "que se sienta más como reproductor local... sin necesidad de estar conectado... no una red social de música" — like putting on a CD and reading the cover, not browsing a feed. Connectivity is for *fetching your own library and its metadata*, not for sharing, discovery feeds, or anything socially-facing. This is why **Share was removed app-wide** (song/playlist/queue share links, the whole "Shares" drawer screen) — hidden from UI, code kept, same pattern as Podcasts/Video/Chat. Weigh any future feature against this: does it help the user play and enjoy music they already have, or does it add a social/networked layer they didn't ask for?
- **Calm over algorithmic.** No fake personalization. Every "smart" feature (Mix, Discover, Recently Played) is built from data the Subsonic API already exposes (genre lists, play history, starred items) — never a recommendation engine. When in doubt, prefer showing the user their own listening history over inventing content.
- **Minimalist over feature-dense — when in doubt, check real Spotify.** The user has pushed back twice now on screens/rows that accumulated too many simultaneous icons/buttons (the album track row went from 3 per-row icons down to a single "⋮" after comparing side-by-side with Spotify screenshots). Default to *fewer* visible controls, with secondary actions behind a single overflow menu, not spread across the row. If unsure whether something is "enough" vs "too much," a real Spotify screenshot of the closest equivalent screen is the fastest way to check before building.
- **Established visual language** (built up incrementally, screen by screen — see "Design system" below).
- **Open vision, not yet detailed: replace the Player's top toolbar and the left navigation drawer with icon-based navigation.** The user doesn't like the current left drawer dropdown. Mentioned in passing while discussing the Player's queue-toggle button placement (2026-08-08) — no concrete design yet, just a direction. See "Current state" item under Player (queue button/secondary row) for the one concrete consequence already acted on: a toolbar action was deliberately left duplicated with a new button because it'll become redundant once this happens, not removed now. Ask for specifics before starting real work on this.
- **Out-of-the-box, zero-config app — the only thing a user should ever configure is the server.** The user's stated end goal (2026-08-08), sharpened significantly the same day when they framed *who this app is actually for*: not the person who sets up the Subsonic server (a "geek"), but whoever that person shares the server with to just listen — a parent, a young cousin, anyone who doesn't know or care what FLAC vs. MP3 or bitrate numbers mean. Their own words: "creo que los clientes de servidores fallan por eso, porque están pensados en gente geek que desarrolla el servidor no en los usuarios comunes." Concretely this has driven three completed passes (see "Current state" items 17-19): removing the theme picker (dark-only now), removing the "Appearance" preference category, and a much larger second pass removing ~15 more settings across every remaining category — anything that's either (a) standard behavior a modern app shouldn't ask about (resume on headphones/bluetooth reconnect, always-visible playback notification), (b) internal tuning nobody but a developer would touch (cache/preload/timeout counts, search result caps), or (c) dead/unreachable (Chat's refresh interval, a Network Timeout setting that turned out to read from nowhere in the codebase). **Not started**: a real fixed brand palette (Spotify-style, greens) instead of the current `Theme.Material3.DynamicColors.Dark` parent, which still derives `colorPrimary` etc. from the device's Material You wallpaper — that dynamic-color dependency is *why* the FAB showed up "vivid purple" earlier in this project. Also floated but explicitly deferred: translating the raw-kbps "Max Bitrate" settings into friendly quality tiers (Low/Normal/High) — a real redesign, not a hardcode-and-remove. Both need the user's input before touching `themes.xml`/`colors.xml` or `settings.xml`'s Network category.

## How we work together

- **Build and device verification are available.** Use Android Studio's bundled JBR (`C:\Program Files\Android\Android Studio\jbr`) with `./gradlew.bat :ultrasonic:assembleDebug`. A Pixel 7 has been available through ADB for installation, UI hierarchy inspection, screenshots, and navigation checks; verify that it is still connected before relying on it. Continue to distinguish clearly between build verification, device interaction, and behavior that still needs user testing.
- **Iterative and screenshot-driven.** The user shares a screenshot, gives specific feedback ("this shadow looks like a floating circle", "the corners are too round"), and expects a concrete fix, not a discussion — unless the request is genuinely ambiguous or has a real design tradeoff, in which case ask first (see next point).
- **Ask before guessing on ambiguous or costly decisions.** Examples from this project: how to pick which artist/genre for the Mix, whether the Mix should regenerate every refresh or persist, how rounded corners should be, whether to hide or delete non-music features. Use targeted questions (2-4 options, not open-ended) rather than picking silently. For unambiguous, well-scoped asks, just implement — don't over-ask.
- **Reuse existing patterns aggressively.** This codebase has established idioms for almost everything: `RefreshableFragment` + `toastingExceptionHandler()` for loading/error state, `BaseAdapter`/MultiType `ItemViewDelegate` classes for RecyclerView rows, `SettingsDelegate` subclasses (`StringSetting`, `BooleanSetting`, etc.) for SharedPreferences-backed state, `NavigationGraphDirections`/`PlayerFragmentDirections` for Safe Args navigation. **Search for the existing pattern before inventing a new one** — several bugs in this project came from not doing that carefully enough (see the bug write-ups in `CHANGES.md`, e.g. the `navArgs()` crash from bypassing a Safe Args action).
- **No git commits or pushes without being explicitly asked.** For most of this project the user didn't want commits at all ("private app, probably won't commit"). Only commit when asked, as a single commit unless told otherwise, and never push anywhere without separate explicit instruction.
- **Keep `CHANGES.md` updated.** Every change gets logged there as it happens, grouped by topic, in Spanish (matching the conversation language), with file paths. Treat it as the project's real changelog — update it in the same turn you make the change, not as an afterthought.
- **Don't over-scope.** When a request implies a much bigger job than the rest of the conversation's pace (e.g. "apply the Home style to every screen" after just finishing Home itself), say so plainly and propose tackling it incrementally rather than silently doing a huge sweep.

## Design system (established incrementally — treat as the current baseline)

- **Surfaces:** neutral dark tones from the Material3 role system (`colorSurfaceContainerHigh` / `colorSurfaceContainerHighest`), not saturated/tonal colors like `colorSecondaryContainer`.
- **Corners:** deliberately more squared than stock Material3 — **4dp** on cards (carousel cards, shortcut grid cards), 16-20dp only on large floating panels (mini player, player control panel, drawer edge). This was an explicit user preference ("mi estilo, apenas suavizado el borde"), not a Material3 default.
- **Text hierarchy:** primary text (song/album/mix title) is **bold**; secondary text (artist, subtitles) is regular weight and muted (`colorOnSurfaceVariant`). Applied to Home's cards. The mini player's title is deliberately *not* bold — it was tuned down from bold earlier for being "too bold" relative to its small cover art, so don't naively re-apply the bold-title rule there without checking with the user.
- **Depth without native elevation on transparent icon buttons.** Android `elevation` draws a shadow from the view's *outline*, not its visible pixels — on a transparent-background `Widget.Material3.Button.IconButton`, that produces a floating disconnected circle (a real bug found and fixed here). Where a subtle shadow is wanted on an icon, it's hand-drawn: the icon is rendered twice in a `<layer-list>`, a dark low-alpha copy offset 1dp behind the normal one (see `media_*_shadow.xml`). Where a shadow is wanted on a whole card/panel (mini player, player control panel), use real `elevation` on a view that actually has an opaque/rounded background — that works fine.
- **Floating card pattern** (mini player): inset from screen edges via `layout_margin`, rounded corners via a dedicated background drawable (not a `MaterialCardView`, just a `<shape>`), slight transparency via `android:alpha` on the whole view (not a true blur — that's a bigger, unimplemented ask if ever wanted).
- **Minimal metadata on the Player screen.** Only title, artist, and playback position/duration are shown. Everything else (album, genre, bitrate, track-in-queue counter, total queue duration) was deliberately removed as clutter; tapping the title navigates to the album where full details live. If asked to add more info back, prefer a tap-through/secondary view over cramming it into the main screen.
- **`FloatingActionButton` is not circular by default under Material3** (it defaults to a fixed rounded-square corner, unlike Material2's full circle) — a real bug found on Artist Detail's and Album Detail's play buttons, which looked like an "out of place" rounded square instead of the intended circular play button. Fix: `app:shapeAppearanceOverlay="@style/ShapeAppearanceOverlay.Ultrasonic.Circle"` (already defined in `styles.xml`, previously only used for circular avatar images). Apply this to any new circular FAB.
- **Icon sizing: use `MaterialButton` (`style="@style/Widget.Material3.Button.IconButton"` + `app:icon`/`app:iconSize`/`app:iconTint`), never a plain `ImageButton` with manual `android:padding` to fake a size.** The padding trick was used for the "⋮" and per-disc download icons and consistently rendered blurry/oversized regardless of the padding math — `ImageButton`'s default `scaleType` doesn't reliably constrain a vector drawable's intrinsic size the way `app:iconSize` does. Found and fixed across `list_item_track.xml`, `list_item_track_album.xml`, and `disc_header_item.xml`; watch for the same pattern anywhere a new small icon-only button gets added.
- **When a screen's top-level list isn't `Track`, extend `MultiListFragment<T>` directly instead of `TrackCollectionFragment`.** `TrackCollectionFragment` carries a lot of Track-specific machinery (selection mode, "⋮" context menu, per-track binders) that buys nothing for a screen listing a different item type, and registering a second delegate for a type `TrackCollectionFragment` already registers unconditionally (e.g. `Album` via `AlbumRowDelegate`) risks an ambiguous override instead of a clean replacement. `MultiListFragment<T>` (the shared base both classes sit on) already provides swipe-refresh, empty state, and the RecyclerView/adapter wiring generically — see `DownloadsFragment` (album cards) vs. `ArtistDetailFragment`'s own separate `albumsAdapter` for its discography grid, both examples of the same pattern.
- **The app's real "offline mode" (`ActiveServerProvider.isOffline()`, a dedicated "Offline" server entry) is a separate concept from "screens that read local/downloaded data."** Offline mode is a global switch that redirects the *entire* app (via `MusicServiceFactory`) to `OfflineMusicService`, hiding network-only actions everywhere (rating, download, add-to-playlist, lyrics, etc.). A screen can read from `offlineMetaDatabase` directly and work with no network regardless of that switch — Downloads does this deliberately, since its whole point is to work even when the user is mid-session online but the thing they tapped happens to only be partially cached. Don't conflate "this screen is local-only" with "the user is in offline mode" when writing future screens.
- **Open, deliberately unresolved: `Ultrasonic.PrimaryText` (`sans-serif-medium`) reads as less crisp/defined than `Ultrasonic.SecondaryText` (`sans-serif-light`) at small sizes on this app's dark surfaces.** Flagged by the user after the Album Detail text-size pass, left as-is for now (explicitly: "dejemos así por ahora pero documenta"). Likely cause: light-on-dark text has a well-known optical "irradiation" effect where stroke edges appear to bleed/halo into the dark background, and it's more pronounced the thicker the stroke — so a medium weight looks comparatively muddier than a light weight at the same small size, even though on a light background the effect would likely read the opposite way. If revisited, the option discussed was dropping title weight further (e.g. to plain `sans-serif` or even reusing `sans-serif-light`) — but `Ultrasonic.PrimaryText` is used app-wide (Home, Artist Detail, Album Detail, mini player, etc.), so treat that as a global design-system change, not a one-screen tweak, and confirm with the user first.

## Current state (high level — `CHANGES.md` has the full detail, including every bug found)

1. **New Home screen**, now the app's start destination (`homeFragment` in the nav graph). Greeting, quick-access buttons, "Recently Played" shortcuts grid, a **daily-persisted genre Mix** (one playlist-style row, regenerates once per calendar day via `Settings.homeMix*` SharedPreferences keys — not a carousel, and not regenerated on every refresh), and album carousels: Favorites, Recently Added, Discover (renamed from "Random" — but that string rename is Home-only, the shared `main.albums_random` string used elsewhere, e.g. sort-order dropdowns, was deliberately left alone).
2. **Drawer & toolbar** modernized.
3. **Mini player** redesigned as a floating card with prev/play/next (was play/pause only).
4. **Full Player screen** trimmed to title/artist/progress; 5-star rating removed in favor of a single-line heart.
5. **Podcasts/Video/Chat hidden** from UI only.
6. Debug builds are labeled "ultrasonic-test".
7. **Media Library redesigned**: Home now exposes horizontal shortcuts for Playlists, Artists, Albums, Songs, and Genres; artist and album lists support compact list/grid views and shared filtering; Songs has library-specific filters and playback behavior; Genres uses artwork-backed cards and opens its songs correctly.
8. **Playlists are functional and redesigned**: server playlists open normally, new playlists can be created by selecting songs, download/removal state is visible, and list/grid modes use four-cover collages. List mode uses genre-inspired horizontal cards; grid mode uses two-column square artwork with labels below.
9. **Artist detail is now dedicated and functional**: selecting a real artist opens `ArtistDetailFragment` instead of the generic album grid. It has a full-width artwork/gradient hero, scroll-revealed toolbar title, play/download-all actions, five compact song shortcuts, and a horizontal album shelf. `getTopSongs` supplies the real Popular ranking when available; `getArtistInfo2` optionally adds an expandable biography and similar-artist carousel. Both endpoints fail softly to the existing search/album data when the server or its external metadata agents cannot supply them. Index/folder entries still follow the legacy track-collection route.
10. **Album detail** now has its own Spotify-style hero (art + gradient + scroll-revealed title), a play/shuffle/download row, and restyled track rows (always-visible track numbers, disc prefix for multi-disc albums, artist hidden for single-artist albums, no per-row rating/cover) — scoped to `TrackCollectionFragment` with `navArgs.isAlbum == true` only, via `AlbumDetailHeaderBinder`/`album_detail_header_item.xml`/`list_item_track_album.xml`. Playlists, genre, artist-songs, starred, all-songs and video keep the original generic header/row untouched (`HeaderViewBinder`/`list_header_album.xml`, `list_item_track.xml`). It also has an optional expandable "About" section (album notes/review) via `getAlbumInfo2`, mirroring Artist Detail's biography — same soft-fail behavior, hidden when unsupported/empty.
11. **Bug audit fixed**: a Home shelf failing no longer blanks the whole screen (each fetch is now caught independently instead of sharing a `coroutineScope` that cancels siblings); Artist Detail's track-fallback chain no longer aborts the whole load when it fails (its documented "soft-fail" behavior now actually holds); genre-song pagination no longer risks skipped/duplicated tracks on fast scrolling; rapid filter/sort switching in Library and Create Playlist no longer risks a stale response overwriting a newer one (both now cancel the previous load job before starting a new one, mirroring `ArtistListModel.setSortOrder()`'s existing pattern).
12. **Track-row interaction model overhauled app-wide** (Album Detail, Playlists, Genre, artist songs, Starred, All songs, Bookmarks — everywhere except the Songs media-library tab, which already had its own row): tapping a track now plays it immediately (previously it toggled a selection checkbox — tap never actually played a song directly in these screens, a real pre-existing bug). Long-press enters a Gmail/Photos-style selection mode instead of opening the context menu, with a circular Spotify-style check indicator (`btn_check_circle.xml`) instead of the old square checkbox, and pressing back while in selection mode exits the mode (clears selection) instead of navigating away — an early version of this got that wrong and was reported/fixed. Outside selection mode, each row shows a single "⋮" icon (opens the same context menu that used to open on long-press — no actions were dropped, "Add to playlist" was added to that menu). An earlier pass had 3 per-row icons (download/add-to-playlist/⋮); that was simplified back down to just "⋮" after comparing against real Spotify screenshots — see the "Minimalist over feature-dense" vision point above. The bottom selection bar shrank from 7 buttons to 2 (download, add to playlist); bulk pin/unpin/delete/play-next/play-last are no longer available for a multi-selection — only per-track via the "⋮" menu. Flag this trade-off to the user if it comes up again; restoring bulk versions of those actions would be a separate follow-up.
13. **"Add to an existing playlist" now exists** (`util/PlaylistUtil.kt`) — it didn't before (only "create a new playlist" existed). Subsonic has no append endpoint, so it works by re-fetching the target playlist's current songs and resubmitting the full list via `createPlaylist(id = ...)`, which Subsonic treats as an overwrite when an id is given.
14. **Share removed app-wide** (song/playlist/queue share links + the "Shares" drawer screen) — hidden, code kept (`ShareHandler`, `SharesFragment` still exist, just unreachable). See the "Local player, not a social network" vision point above for why.
15. **Album Detail: second on-device feedback round.** Track numbers are no longer force-shown on album rows — they now respect `Settings.shouldShowTrackNumber` like every other screen (default off), reverting the earlier "always show, with disc-prefix like '1-03'" decision. For multi-disc albums, disc grouping is now a small divider row ("Disc N" + a line, new `DiscHeader` item type/`DiscHeaderBinder`) inserted between tracks at disc boundaries, instead of a number prefix. The header's standalone download button was removed (only shuffle + play remain there); whole-album download is via multi-select + the bottom bar, or per-track via "⋮". Added breathing room between the selection checkbox and the track-number column.
16. **Downloads is a real download manager**, not just a functional track list. It went through two rewrites:
    - First: made functional at all — it was read-only before (no tap, no context menu, no delete/unpin; the original devs had left TODOs about this), rebuilt on `TrackCollectionFragment` like `BookmarksFragment`. Its data source was also corrected after an on-device bug report (tracks downloaded in a previous session showed nothing): the first version used `DownloadService.observableDownloads`, which only reflects the *active download queue* — a track drops out of it the moment its download finishes, it's a progress indicator, not a downloaded-library catalog. **If any screen/feature needs "what's actually downloaded," always read `activeServerProvider.offlineMetaDatabase.trackDao()`, never `observableDownloads`.**
    - Second, after the user clarified they wanted it to look like Playlists (cards, not a flat list) and confirmed it should function as a proper download manager: **`DownloadsFragment` now extends `MultiListFragment<Album>` directly, not `TrackCollectionFragment`.** It shows one card per downloaded album (`DownloadedAlbumRowBinder`/`list_item_downloaded_album.xml`, same visual language as Playlists' cards), grouped/counted from the same `trackDao()`/`albumDao()` local database, each with its own remove-download action. Tapping a card opens `DownloadedAlbumFragment` (new, thin `TrackCollectionFragment` subclass, `isAlbum = true`) which reuses the existing Album Detail hero/disc-grouping UI but loads tracks via `getDownloadedAlbumTracks()` — **always local-only, deliberately not the normal `toTrackCollection`/`getAlbumAsDir` network path**, so the whole flow keeps working with zero connectivity instead of erroring out or showing tracks that were never actually downloaded for a partially-grabbed album. `MultiListFragment` (not `TrackCollectionFragment`) turned out to be the right base whenever a screen's *top-level* list isn't tracks — see the new design-system note below.

17. **Theme picker removed — the app is dark-only now, no user setting.** `Settings.theme` and its 4 variants (`UltrasonicTheme.DayNight/.Dark/.Black/.Light`) are gone; `Util.applyTheme()` always applies `UltrasonicTheme.Dark`. Also removed as dead weight once nothing could trigger it: the `RxBus.themeChangedEvent*` publisher/observable and the `NavigationActivity` subscription that used to call `recreate()` on theme change. Still uses `Theme.Material3.DynamicColors.Dark` as the parent (so `colorPrimary` etc. still follow the device wallpaper) — see the vision note above for the follow-up (a real fixed palette) this sets up but doesn't do yet.

18. **Settings: "Appearance" category removed entirely, hardcoded instead.** Direct extension of the out-of-the-box vision (see above) — driven by real device feedback on the Settings screenshot. `Settings.kt`'s `shouldDisplayBitrateWithArtist`, `shouldUseFolderForArtistName`, `shouldShowTrackNumber`, `serverScaling` are now `const val`s fixed at their prior real behavior (not necessarily the `BooleanSetting` delegate's fallback default — a few of those didn't actually match the XML-declared default or what the screenshot showed, so the *actual current behavior* was used as source of truth, not either declared default). `shouldSortByDisc` is the one real behavior change: fixed to `true` (was `false`), confirmed explicitly — sorting by disc is strictly more correct for multi-disc albums and has no effect on single-disc ones. `showNowPlayingDetails` was deleted outright rather than fixed — already dead code, nothing reads it since those fields left the Player screen earlier this session. **Before hardcoding anything under "Appearance," each option was checked for whether it was actually a style preference vs. a server/library-compatibility switch in disguise** — `shouldUseFolderForArtistName` depends on whether the user's server library has proper ID3 tags, confirmed with the user before fixing it, not assumed. Also removed as a side effect: the entire "Appearance" `PreferenceCategory` (now empty) and the dead "Show details in Now Playing" switch under "Playback Control."
19. **Search: live filtering as you type, debounced.** Search hits the server on every query (no local list to filter client-side), so true per-keystroke requests would hammer it — `NavigationActivity.scheduleLiveSearch()` waits 400ms of typing pause, requires 2+ characters, and skips repeated/unchanged queries before navigating to `searchFragment` (using `NavOptions` singleTop + popUpTo so refining a query replaces the existing back-stack entry instead of stacking one per keystroke). Explicit submit (IME search key, voice search) is untouched — still the original `ACTION_SEARCH` intent path, which is also the only path that saves to recent-search suggestions (live keystrokes deliberately don't). `SearchFragment.search()` also now cancels its previous in-flight `Job` before launching a new one, so a slow response to an old query can't land after and overwrite newer results. Only launch-tested (no crash), not interactively verified on a device — the debounce feel/timing in particular needs a real trial.
20. **Settings: second, much larger simplification pass — ~15 more settings removed.** Triggered by the user's reframing of who the app is for (see vision section). Every remaining category was audited setting-by-setting for "would a non-technical listener ever touch this" before removing anything — an `Explore` agent traced every single call site first so nothing broke silently. Fixed-and-removed: `resumePlayOnHeadphonePlug=true`; Bluetooth resume/pause collapsed from a 3-way user choice (all-devices/A2DP-only/disabled) down to fixed A2DP-only for both (`BluetoothIntentReceiver.kt` simplified accordingly, the custom picker dialog and `Constants.PREFERENCE_VALUE_*` deleted from `SettingsFragment.kt`); `showNowPlaying=true` (the whole now-empty "Notifications" category went with it); `chatRefreshInterval` fixed at its old default purely so the already-unreachable `ChatFragment.kt` keeps compiling; `preloadCount=3`, `parallelDownloads=3`, `directoryCacheTime=300`; all 6 Search count settings fixed at their old defaults (`defaultArtists=3/maxArtists=10/defaultAlbums=5/maxAlbums=20/defaultSongs=10/maxSongs=25`) — **note `maxAlbums`/`maxSongs` double as generic page-size defaults well beyond Search** (Browse grids, "Play Random Songs," playlist creation, any track-collection screen without an explicit size), so their old values were kept exactly to avoid changing behavior anywhere else; `seekInterval=5000`ms (the `seekIntervalMillis` computed property is actually *seconds* despite its name — pre-existing naming bug, documented not fixed, both units are genuinely used by different playback paths); `shouldShowArtistPicture=true`; `scrobbleEnabled=true` (no per-server capability flag exists for scrobble, unlike chat/bookmarks/shares, so there's nothing to auto-detect — it's now unconditional and a no-op on servers with nothing configured to scrobble to). **Deleted outright** (not just hardcoded): the "Network Timeout" setting — turned out nothing in the entire codebase reads it, a fully dead preference row; "Hide media from other apps" — had no `Settings.kt` property at all, lived only as a reactive `.nomedia`-folder toggle in `SettingsFragment.kt` with no startup-time enforcement, removed per explicit user preference (they don't want their music hidden from other apps). Categories left standing (Playback Control, Network, Music Cache, Other, Debug) kept everything that's a genuine functional choice (ID3 tag mode, bitrate caps, ReplayGain, hardware offload, language override) — those are compatibility/preference decisions, not tuning noise. Only launch-tested, the Settings screen itself has not been reopened and eyeballed since this pass.
